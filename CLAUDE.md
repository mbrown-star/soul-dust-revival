### Stack
Next.js 16 (App Router, React 19, strict TypeScript) · Cloudflare Workers via the OpenNext adapter (`@opennextjs/cloudflare`) · Supabase Auth (magic link) + Postgres via Drizzle ORM · Stripe (webhook-driven entitlements) · Cloudflare Stream and R2 · Resend · Zod · Tiptap · DOMPurify · Tailwind.

### Commands
```
npm run dev          # local dev server
npm run typecheck    # tsc --noEmit
npm run lint         # eslint
npm run build        # next build
npm run test         # vitest — needs a running local Postgres (see BUILD_TASKS.md)
npm run verify       # typecheck + lint + build — must pass clean
npm run preview      # build + run in the real Workers runtime locally (wrangler)
npm run cf:deploy    # build + deploy to Cloudflare
npm run db:generate && npm run db:migrate
npm run db:seed
```
`npm test` isn't part of `npm run verify` — it needs a real database connection,
which isn't guaranteed in every environment that runs `verify` (e.g. CI without a
Postgres service configured). Run it explicitly, and always before calling checkout/
webhook/entitlement changes done.

### Scaffold rules
- **Reuse before writing.** Use the scaffold's existing modules and patterns, especially these single sources of truth:
  - `lib/entitlements/check.ts` for every content access check
  - `lib/admin/guard.ts` (`requireAdmin`, `requireLeaderOrAdmin`, `requireRole`) for every role check
  - `lib/validation/schemas.ts` for every API input
  - `lib/db/schema.ts` for the data model
- **Never bypass those.** Do not query `users.role` directly, re-implement access checks, or accept unvalidated input in a route.
- **Customize without forking where possible.** Prefer config, new files, and extension points over rewriting scaffold internals. List unavoidable changes to scaffold-origin code under "Scaffold deviations" so upstream fixes can still be merged.
- **Brand:** keep the design system (ink, dusk, parchment, ember, gold, moss; Fraunces, Source Serif 4, Archivo) unless told otherwise.
- **Scaffold code is in scope for both reviews.** Inherited code, dependencies, default configs, and seed data are reviewed too. Report scaffold-origin findings separately from new-code findings.
- **On scaffold updates,** re-run both reviews against the whole updated scaffold, not just the diff.

- **2026-11-03 — book cover PDF upload + front/back cover gallery (new feature).** Admins now upload a single full-wrap cover PDF (back cover + spine + front cover, as KDP's print-cover template produces) for `type: "book"` products instead of a plain image. New route `app/api/admin/products/cover-pdf/route.ts` extracts the embedded raster image via `unpdf`, crops it down the middle via `@cf-wasm/photon` (new dependencies — chosen after researching Cloudflare Workers/edge compatibility; ruled out `mupdf.js` for true PDF rendering specifically because it's AGPL-3.0-licensed, incompatible with this closed-source product without a paid license), and stores all three results (source PDF + back + front JPEGs) in R2 under server-generated `crypto.randomUUID()` keys — never a client-supplied key. New `products` columns: `backImageUrl`, `backImageAlt`, `coverPdfUrl` (migration `drizzle/0001_warm_rockslide.sql`, purely additive/nullable). No spine-width detection — the page is just cut 50/50 per an explicit decision, since the admin didn't want to collect page-count/trim-size metadata to compute it precisely. Storefront detail page shows a scrollable front/back gallery (`components/commerce/CoverGallery.tsx`); list views still show the front cover only (the existing `imageUrl` field, repurposed to mean "front cover" for book products). Required reviews run against this feature specifically found and fixed: a High-severity DoS risk (a crafted PDF could decode to an arbitrarily large pixel buffer before any size check ran — added a pre-decode physical-page-size guard plus a post-extraction pixel-count cap, both in `lib/images/bookCover.ts`), a High-severity code-quality gap (alt text for `imageUrl`/`backImageUrl` was enforced only in the admin UI, not the API schema — added `.refine()` checks to `productSchema`, the same class of bug this file's history already shows happened twice before), a cross-browser scrollbar-hiding gap in the gallery (Firefox-only `scrollbarWidth` with no `-webkit-` equivalent), and an untested/unhandled corrupt-PDF path (now mapped to a clean 400 instead of a raw 500). **Deferred, not fixed**: no cleanup of a product's previous cover PDF/images in R2 when it's re-uploaded (storage grows unbounded across replacements — low severity, matches the existing `studies/import` route's same behavior); multiple embedded images in one PDF silently takes the first one found rather than erroring.
- **2026-11-03 — Amazon/Stripe purchase routing for physical products.** Physical books are mostly sold through Amazon rather than our own Stripe checkout, so `products` now has `amazonUrl` (nullable) and `sellOnStripe` (boolean, default `true`). The storefront detail page (`app/(marketing)/books/[slug]/page.tsx`) renders a Stripe "Buy Now" button (`components/commerce/AddToCartButton.tsx`, renamed from "Add to cart") when `sellOnStripe` is true, and/or a "Buy on Amazon" link-out button (new `components/commerce/AmazonBuyButton.tsx`) when `amazonUrl` is set — a product can show one or both. Digital products are restricted to Stripe-only (`productSchema` refines reject `amazonUrl`/`sellOnStripe: false` on `format: "digital"`), since entitlements are only ever granted off the Stripe webhook and an Amazon sale has no way to trigger that. The admin product form (`components/admin/ProductForm.tsx`) gates the Amazon checkbox/URL field to physical products and requires at least one route enabled. Security review of this build found and fixed: (1) **Domain-validation bypass, High** — the first version of the `amazonUrl` Zod validator was a regex matched against the *raw URL string*, anchored only at the start (`^https:\/\/...amazon\.[a-z.]+\/`), not at the end of the hostname; a value like `https://amazon.com.evil.com/x` satisfied it even though its real registrable domain is `evil.com`, and a URL-encoded userinfo trick (`https://amazon.com@evil.com/`) would read as "amazon.com" to a human glancing at the stored value. Fixed by parsing the URL and validating `url.protocol === "https:"` plus an end-anchored regex against `url.hostname` only (`lib/validation/schemas.ts`), with regression tests for both bypasses in `lib/validation/schemas.test.ts`. (2) **Business-logic/authorization gap, Medium** — `/api/checkout` validated that each requested product existed and was `active`, but not `sellOnStripe`; a crafted request could still buy a product an admin had marked Amazon-exclusive through our own Stripe checkout, bypassing the sales channel the admin configured. Fixed by rejecting any `sellOnStripe: false` product in the checkout route, with a regression test in `app/api/checkout/route.test.ts`. 138 tests pass, `npm run verify` is clean. **Note:** while verifying this build, `npm run db:migrate` (drizzle-kit) was found to fail unrelated to this change — `drizzle.config.ts`'s `MIGRATION_DATABASE_URL` read returns empty inside drizzle-kit's own process even though it resolves correctly in a plain Node script using the same `process.loadEnvFile(".env.local")` pattern — so migration 0002 (`drizzle/0002_medical_madame_hydra.sql`) was applied directly via a one-off script instead. This is a pre-existing tooling issue, not introduced by this build; flagging since it'll block the next `db:migrate` too until someone investigates drizzle-kit's env handling.
- **2026-11-04 — real Supabase project connected; `db:migrate`'s drizzle-kit env bug worked around, and the untracked migration 0002 fixed.** Connected `.env.local` to the real "Soul Dust Revival Website/Web App Project" Supabase project (already had the full 17-table schema from earlier manual work, all rows empty). `npm run db:migrate` still hits the `drizzle-kit` env-loading bug noted just above (`MIGRATION_DATABASE_URL` resolves empty inside drizzle-kit's own process) — worked around the same way, by pre-loading `.env.local` into `process.env` in a parent Node process and `spawnSync`-ing `npx drizzle-kit migrate` inheriting that populated env; still unresolved at the tooling level, same root cause as before. That run then failed a second way: migration 0002 (applied via the one-off script mentioned above) was never recorded in `drizzle.__drizzle_migrations`, so drizzle-kit tried to re-run its `ALTER TABLE ADD COLUMN` statements against columns that already existed, erroring without a useful message (just the connection's own NOTICE output, then a bare exit 1). Fixed by inserting the correct row directly: `hash` = `sha256` of the full migration file's contents (confirmed by recomputing it for migrations 0000/0001 and matching the two rows already present — drizzle-kit hashes the raw file text, not a normalized version), `created_at` = that migration's `when` timestamp from `drizzle/meta/_journal.json`. `db:migrate` now runs clean (exit 0, "migrations applied successfully!"). - **2026-11-03 — full SECURITY_REVIEW.md checklist pass (5 parallel sub-reviews + npm audit).** Found 1 High, 4 Medium, 3 Low; all but one Medium and two Lows fixed in this build. Fixed: (1) **SSRF, High** — `publishToX` (`lib/social/publishers/x.ts`) fetched an admin-supplied `imageUrl` server-side with no host restriction, letting a compromised/malicious admin session make the server fetch arbitrary internal addresses; now restricted to the app's own `R2_PUBLIC_BASE_URL` origin, with a regression test in `lib/social/publishers/x.test.ts`. (2) **Auth cookie missing `Secure`, Medium** — `@supabase/ssr`'s library default cookie options don't set `secure` at all; both `lib/supabase/server.ts` and `lib/supabase/client.ts` now pass `cookieOptions: { secure: true, sameSite: "lax" }` explicitly. (3) **Blog markdown not sanitized on write, Medium** — `app/api/admin/blog/posts/route.ts` stored raw markdown with no DOMPurify pass, unlike content-blocks/leader-resources which both sanitize on write; added the same `DOMPurify.sanitize` call to both POST and PATCH, plus a regression test. (4) **Encrypted tokens over-serialized to the client, Medium** — `app/admin/settings/connections/page.tsx` passed full `integration_connections` DB rows (including encrypted token ciphertext, internal ids, expiry metadata) into a client component that only renders `displayName`/`status`/`lastError`; now mapped down to just those three fields before being passed across the server/client boundary. (5) **Low** — centralized `app/api/stream/sign-url/route.ts`'s inline Zod schema into `lib/validation/schemas.ts` (`streamSignUrlSchema`), and added schema validation to `app/api/admin/leader-resources/route.ts`'s `DELETE` handler (previously read `id` with no validation at all). **Deferred, needs a decision:** direct-to-R2 presigned PUT uploads (`lib/r2/upload.ts`) have no enforced size cap — query-string-presigned S3/R2 PUT URLs don't straightforwardly support a hard max like a presigned-POST policy would, and implementing this correctly needs either a policy-based upload flow (client-side rework) or live R2 testing to confirm enforcement actually works, neither of which this build verified; and OAuth `redirect_uri` construction (`app/api/admin/connections/{facebook,x}/{authorize,callback}/route.ts`) uses `req.nextUrl.origin` rather than a fixed `APP_URL` env var — low risk today since Meta/X independently reject any unregistered redirect_uri, but hardening this means adding a new required env var and touching ~10 call sites, out of scope for this build. `npm audit`: 26 vulnerabilities (22 moderate, 4 high), all in devDependencies/build tooling (eslint, drizzle-kit/esbuild dev server, `@opennextjs/*` build chain) — zero in the production runtime dependency tree.
- **2026-11-03 — upload key validation let `..` path segments through; token-cipher malformed-check had two false-positive/negative gaps (test-suite expansion).** Added unit tests for `lib/validation/schemas.ts`, `lib/crypto/tokenCipher.ts`, `lib/stream/signing.ts`, `lib/admin/guard.ts`, and `lib/email/send.ts` (previously untested). Found and fixed: (1) `uploadUrlSchema`/`resourceFileUploadUrlSchema`'s character-allowlist regex permitted `.` and `/`, so a key like `../../etc/passwd` passed — added a `.refine` rejecting any `..` path segment (`r2KeySchema` in `lib/validation/schemas.ts`). (2) `tokenCipher.ts`'s `decryptToken` falsy-checked the split segments, wrongly rejecting a legitimate empty-ciphertext data segment (encrypting `""`) as malformed — changed to a length check, then added a stricter check that the iv/authTag segments decode to their fixed sizes (12/16 bytes) so a truncated value still gets the deliberate "Malformed encrypted token" error instead of a raw Node crypto error. **Deferred, not fixed:** `uploadUrlSchema`/`resourceFileUploadUrlSchema` still accept an arbitrary client-supplied R2 key (only scoped by the regex + `..`-refine), which doesn't match `SECURITY.md`'s stated design that upload keys are always server-generated as `{random-uuid}.{extension}`. Both routes require `requireAdmin()` first, so this isn't a pre-auth vuln, but it's inconsistent with the documented model and the fix (always generating the key server-side) is a larger change to `app/api/admin/upload-url/route.ts` / `app/api/admin/leader-file-upload-url/route.ts` than this build's scope — needs a decision before changing those routes' contract.
- **2026-11-03 — missing SSL enforcement on all Postgres connections (security finding, scaffold-origin).** Neither `lib/db/client.ts` (runtime) nor `drizzle.config.ts` (migrations) told the `postgres` driver to use TLS, and the driver does not infer it from a plain Supabase connection string — it silently connects without SSL, which Supabase then rejects (`drizzle-kit migrate` surfaced this as an indefinite hang rather than a clean error; the app's runtime queries would have failed the same way). Fixed: `lib/db/client.ts` now passes `ssl: "require"` as a client option. `drizzle-kit` (v0.31.11) does not honor a separate `ssl` config field once a `url` is also set, so `drizzle.config.ts` instead appends `sslmode=require` directly onto the connection string it builds from `MIGRATION_DATABASE_URL`. Data-in-transit encryption to the database was effectively unenforced before this fix — see SECURITY_REVIEW.md §5 (Data protection).
- **2026-11-03 — `RESEND_FROM_EMAIL` is a bare address; display name lives in code (scaffold-origin).** `lib/env.ts` validates `RESEND_FROM_EMAIL` with `z.string().email()`, which rejects the `"Name <email>"` form. `lib/email/send.ts` now builds `from: \`Soul Dust Revival <${process.env.RESEND_FROM_EMAIL}>\`` instead of putting the display name in the env var, and the old `?? "orders@yourdomain.com"` placeholder fallback was removed since the env var is now always set. If a second sender identity is ever needed, add a separate env var rather than overloading this one.
- **2026-11-03 — `CLOUDFLARE_STREAM_SIGNING_KEY` stored/used as a raw PEM (scaffold-origin bug, found during real Stream setup).** `lib/stream/signing.ts` passed `process.env.CLOUDFLARE_STREAM_SIGNING_KEY` straight into `jwt.sign()` as a PEM string, but Cloudflare's `/stream/keys` endpoint returns the private key **base64-encoded**, and a raw multi-line PEM is also fragile to round-trip correctly through `.env` parsing across Next.js, Node's `loadEnvFile`, and vitest. Fixed: the env var now holds the base64 string Cloudflare returns as-is, and `signing.ts` decodes it (`Buffer.from(..., "base64").toString("utf-8")`) before passing it to `jwt.sign()`. Verified against a real signing key generated via the Cloudflare API: decodes to a valid RSA private key (`crypto.createPrivateKey` succeeds). Note for whoever regenerates this key later: store exactly what the API returns in `pem`, do not re-encode or reformat it.
- **`drizzle.config.ts`** reads `MIGRATION_DATABASE_URL` instead of `DATABASE_URL`. `drizzle-kit migrate` needs session-level Postgres features (advisory locks, multi-statement DDL transactions) that Supabase's transaction-mode pooler (used by `DATABASE_URL` at runtime, required for edge/serverless) doesn't support. Migrations use a separate session-pooler connection string instead. `lib/db/client.ts` is unchanged and still uses `DATABASE_URL` on the transaction pooler. `MIGRATION_DATABASE_URL` added to `.env.example`; intentionally not added to `lib/env.ts`'s schema since it's only read by the standalone `drizzle-kit` CLI, never by the Next.js runtime.

## Required review on every build

Every build of Soul Dust Revival must pass both reviews below before it is called complete. This applies to features, fixes, and refactors alike.

- Security review: @SECURITY_REVIEW.md
- Code quality review: @CODE_QUALITY_REVIEW.md

### Build workflow
1. **Plan.** Confirm the requirement, read the relevant scaffold docs, and list the files likely to change.
2. **Build.** Implement following scaffold patterns. Keep secrets out of code from the start.
3. **Verify.** Run `npm run verify` and any tests. Fix every failure; do not suppress errors or lint rules to get green.
4. **Review.** Run both reviews against everything changed in this build, including the automated and AI-assisted testing tiers that apply (see SECURITY_REVIEW.md). Active scans and AI pentests run only against local or staging, never production.
5. **Fix.** Resolve all Critical and High findings from both reviews, then re-run `npm run verify`.
6. **Document.** Update `BUILD_TASKS.md` (and `SECURITY.md`, `PRIVACY.md`, `ACCESSIBILITY.md` when behavior in those areas changes).
7. **Report.** End every build with: what changed, `verify` result, security review result, code quality review result, scaffold deviations added, and any deferred findings with reason. Do not mark the build done if either review fails.

### Rules
- Never skip a review because the change looks small. If a section does not apply, say so in the report.
- Never commit secrets or personal data. `.env` stays git-ignored.
- Ask before adding dependencies, changing the database schema in a destructive way, or deferring any Critical or High finding.
- Ask before destructive actions (deleting data, force pushes, dropping tables, production deploys).
- Some work cannot be verified without live credentials (Stripe, R2, Stream, Supabase, Meta, X). State clearly what was and was not verified; never claim an integration works when only the types were checked.
- When these instructions conflict with a request, flag the conflict and ask.

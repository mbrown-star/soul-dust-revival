# QA Findings — 2026-11-07

First full run of the new QA regression suite (`qa/`) against local dev, isolated test
Postgres, comprehensive fixtures covering every product format/study state/role. 390
automated checks (195 × desktop-chromium, 195 × mobile-chromium) all pass; this report is
everything found *beyond* "does it crash" — real bugs, confirmed-still-present documented
gaps, and UI/UX opportunities, with device-format coverage (desktop/laptop/tablet/mobile)
called out specifically per request.

**How findings were produced:** reading every piece of source touched, writing an
automated assertion or a manual checklist step against real fixture data, running it,
and for anything surprising, reading the actual component/route code to confirm root
cause before reporting it here — not guessed from memory of CLAUDE.md's history. Each
item below cites the file/line it was confirmed against.

---

## Critical / High

### 1. Public nav bar is completely unusable at mobile widths — confirmed, severe
**Where:** `components/marketing/SiteHeaderShell.tsx` + `components/marketing/SiteNav.tsx`
**Confirmed:** at a 375px viewport (iPhone SE/mini-class width), a logged-in user's nav
bar overflows off-screen. "Cart", "My Library", and "Profile" render past the right edge
of the viewport with **no way to reach them at all** — not by tap, not by scroll.
Confirmed via `document.documentElement.scrollWidth === clientWidth` (375 = 375): there is
no horizontal scroll anywhere on the page, not even at the document level. This means
**a logged-in mobile visitor cannot open their Profile menu, cannot reach Account, cannot
log out, and (if admin) cannot reach the Admin link** — all through the primary nav.
Unlike the admin nav (`AdminNav.tsx`), which has an explicit horizontal-scroll fallback
for exactly this situation (CLAUDE.md, 2026-11-05), the public `SiteNav`/`SiteHeaderShell`
have no responsive handling at all: no hamburger menu, no `flex-wrap`, no
`overflow-x-auto`.
**For a logged-out visitor**, the symptom is different but still broken: nav items wrap
mid-word ("Books" / "&" / "Studies" on three lines; "Log" / "in" split across two) —
screenshotted at 375px. This makes the header extremely tall and visually broken.
**Compounding bug:** because the header is `sticky`, and its height grows substantially
when the nav wraps to 3 lines on mobile, page content scrolls *underneath* the taller
header and gets visually clipped/overlapped — confirmed on `/books/qa-bundle-both-formats`
at 375px, where the "Ships within a few business days..." copy is overlapped by the nav.
**Regression-tracked** in `qa/e2e/specs/public-marketing.spec.ts` (the two Profile-menu
tests directly assert the overflow's bounding box on the mobile project, so a real fix
will make those assertions fail and need updating — intentional, this is a pin, not a skip).
**Recommendation:** give `SiteNav` the same `overflow-x-auto` + `no-scrollbar` treatment
`AdminNav` already has as a quick mitigation, or (better, given how broken this is) a real
responsive collapse (hamburger/sheet menu) below a chosen breakpoint.

### 2. My Library shows the study's raw internal title, never the product's storefront title
**Where:** `components/study/LibraryCard.tsx:56` + `app/(study-app)/library/page.tsx`
(query only selects from `studies`, no join to `products`)
**Confirmed:** a customer who bought "QA Devotional — In Progress" (the clear product
title shown on `/books` and at checkout) sees **"QA Devotional Fixture"** (the internal
`studies.title` column) on their own My Library page — a different string than what they
purchased. This is the *same underlying problem* CLAUDE.md already documents for
`/studies/[slug]`'s own page (the real Psalms devotional's `studies.title` is a raw import
filename with underscores) — but confirmed here to be **broader than previously
documented**: it also affects My Library, the page a customer visits most often, not just
one less-common route. `DevotionalAppView`'s own header was specifically fixed to read the
product title instead (CLAUDE.md, 2026-11-10) — My Library was apparently never given the
same fix.
**Recommendation:** either join `products` in the My Library query and display
`product.title`, or (simpler) treat this as one root-cause fix: make `studies.title`
itself always mirror its linked product's title at write time, so every reader of
`studies.title` is automatically correct instead of each call site needing its own
product-title lookup.

### 3. Study tab's first "Part" is open by default but is never marked read — understates progress, confusing click
**Where:** `components/study/study-tabs/StudyTab.tsx:29,33-37`
**Confirmed live:** `const [openPart, setOpenPart] = useState<number | null>(0)` — Part 1's
content is visible the instant the Study tab loads, with **no click needed**. But
`openPartAndMarkRead()` (which calls `togglePart` to mark a part read) only ever runs
**inside the click handler** — never on mount. Two consequences, both reproduced directly:
(a) a reader who simply reads the already-open Part 1 and moves on gets credit for **"0 of
2 parts read,"** understating real progress — they can never reach 100% without
realizing they need to close-then-reopen Part 1 specifically; (b) clicking the already-open
"Part 1" header — the single most natural first action for a new reader, who has no way to
know it's already expanded — **collapses it** instead of opening it, the opposite of what
a user would expect.
**Recommendation:** either default `openPart` to `null` (nothing open until clicked,
standard accordion behavior, and the first click then correctly marks it read), or call the
mark-read logic once on mount if an open-by-default first part is the intended UX.

### 4. Checkout success page: wrong price shown and a duplicate line collapsed for "both"-format orders
**Where:** `app/(marketing)/checkout/success/page.tsx:40-58`
**Confirmed by reading the code:** `orderedProducts` is built via
`db.select().from(products).where(inArray(products.id, productIds))` — `productIds` comes
from `orderItems`, and for a `format: "both"` purchase, Stripe/the webhook produce **two**
order_items referencing the **same** `productId` (one `variant: "physical"`, one
`variant: "digital"`, per `order_items.variant`). The `inArray` select returns that product
row only **once**, so a customer who bought both halves of a "both" product sees only
**one** line on their confirmation page, priced at `p.priceCents` — which the schema
documents as **always the physical price** for a "both" product
(`lib/db/schema.ts:81`, "physical price for 'both'"). The digital price
(`digitalPriceCents`) is never read here. The bottom "Total" is correct (it comes from
`order.totalCents`, computed correctly elsewhere) — so the visible effect is a line-item
total that doesn't add up to the grand total, which reads as a pricing error to the
customer even though they weren't actually overcharged.
**Recommendation:** iterate `orderItems` directly (not deduped `products`), joining each
item to its product and picking `variant === "digital" ? digitalPriceCents : priceCents`,
so a two-line "both" order renders as two distinct lines with their real individual prices.

## Medium

### 5. `/account` has no session guard at all — a guest gets stuck on "Loading..." forever
**Where:** `app/(marketing)/account/page.tsx` (no `getSession()`/redirect, unlike
`/library`'s page.tsx) and `AccountPageClient.tsx:55` (a `"Loading..."` state with no
`useEffect` path that redirects an unauthenticated visitor anywhere).
**Confirmed by reading both files.** A logged-out visitor who navigates to `/account`
directly sees a perpetual loading spinner with no error, no redirect, no next step — not a
security hole (no data renders), but a real dead-end UX gap every other gated page in this
app (`/library`, `/admin/*`, `/leader`) avoids.

### 6. `/account` has no order-history UI at all
**Where:** `AccountPageClient.tsx` (confirmed by reading: only email, data export, and
account deletion are present — no query against `orders`/`order_items` anywhere in this
component or its page).
qa-user has one real `paid` order and one real `pending` order seeded (see
`qa/CONVENTIONS.md`'s fixture table) with nowhere in the UI to see either one. A customer
has no self-service way to check an order's status or review what they bought.

### 7. Neither `/login` nor `/signup` redirect an already-authenticated visitor
**Confirmed:** both pages render their forms unconditionally regardless of session state.
An already-logged-in user who navigates back to `/login` sees a login form instead of
being bounced to `/library` — a minor but real UX inconsistency with how every other
"wrong state for this page" case in the app is handled.

### 8. Admin: no UI path exists to edit a Study-kind lesson's structured content at all
**Where:** `app/admin/studies/[id]/lessons/[lessonId]/page.tsx:35` renders only
`LessonBlockEditor` (against `content_blocks`) — confirmed no component anywhere reads or
writes `lessons.studyContent` (the subtitle, full passage, Work the Word stations, prayer
beats, benediction, etc. that drive the entire 5-tab Study reader).
**Impact:** every real, live Colossians-style week can currently only ever be created or
corrected via the one-off `scripts/backfill-colossians-study-content.ts`-style scripts
this project has written for each new batch of content — there's no way for an admin to
fix a typo in a Study's key verse, add a Greek station, or edit a prayer beat through the
admin console itself.

### 9. Admin Studies list has no Kind (Study vs. Devotional) indicator
**Where:** `app/admin/studies/page.tsx` — confirmed by reading: the row renders only
title, slug, and published status. An admin cannot tell a devotional from an interactive
study without opening each one individually.

### 10. Admin nav bar has no active-section indicator
**Where:** `components/admin/AdminNav.tsx` — confirmed no `aria-current`, no active-state
class anywhere in the component. An admin looking at the nav while on, say, `/admin/blog`
has no visual confirmation of which section they're currently in.

## Device format findings (desktop / laptop / tablet / mobile)

Tested at four representative widths: mobile (375×812), tablet (768×1024), laptop
(1366×800), and desktop (the pane's own width, ~1280+). Full Playwright suite also runs a
real mobile-viewport project (`mobile-chromium`, Pixel 7 emulation) across all 195
specs, not just the pages spot-checked visually below.

| Width class | Verdict | Notes |
|---|---|---|
| **Mobile (375px)** | **Broken** | Findings #1 above (nav totally unreachable when logged in; wraps ugly when logged out; sticky header overlaps content) are mobile-only — none reproduce at tablet width or above. This is the one device class that needs real design attention before the site is genuinely mobile-ready. |
| **Tablet (768px)** | Clean | Homepage, featured-content grid, nav bar all render correctly with no overflow or wrapping. Two-column card grid reads well. |
| **Laptop (1366px)** | Clean | Product detail's two-column layout (cover + purchase panel) is well-proportioned; nav bar has ample room. |
| **Desktop (1280px+)** | Clean | This is the width the app has clearly been designed and tested against throughout this project's history — no new findings here beyond what's already in this report. |

**Additional mobile-specific item, lower severity:** `components/study/Sheet.tsx` (the
shared Greek-word/week-picker bottom sheet) has `items-end` positioning on mobile with no
`env(safe-area-inset-bottom)` padding — confirmed by reading the component. Its last
action button sits flush against the very bottom edge of the viewport. On a real
notched/gesture-navigation phone (any iPhone X or later, most modern Android phones), the
OS's own home-indicator/gesture bar occupies that same strip of screen, which can make a
flush-bottom button partially obscured or awkward to tap reliably. (Reproduced directly in
this environment via a different, dev-only cause — Next.js's dev-mode indicator badge,
which doesn't exist in production — but the underlying missing safe-area padding is real
and worth adding regardless of what originally surfaced it.)

**Not yet checked:** real iOS Safari / Android Chrome on physical hardware (this pass used
Chromium's device emulation only, which doesn't model Safari's own viewport/scroll quirks
or a real on-screen keyboard's effect on layout) — worth a pass on real devices before
calling mobile done, especially given finding #1's severity.

## The suite itself

This report was produced by, and can be re-produced with, the new `qa/` regression suite:

- `qa/README.md` — setup and how to run
- `qa/CONVENTIONS.md` — fixture inventory, spec/checklist templates
- `qa/e2e/specs/*.spec.ts` — 195 automated Playwright checks across public storefront,
  checkout, account/auth, My Library/entitlements, the Study reader, the Devotional
  reader, the full admin console (access control + CRUD for all 8 sections), social
  scheduling, settings/connections, and cron endpoint auth — run on both a desktop and a
  real mobile-viewport project
- `qa/checklists/*.md` — 10 manual, judgment-level walkthroughs (copy, visual consistency,
  accessibility, cross-cutting "is this information actually true" checks) for whatever
  automation can't catch
- `qa/scripts/seed-qa.ts` / `cleanup-qa.ts` — safe, idempotent fixture management, fully
  isolated from the real database

Re-run after any future build item: `npm run qa:seed && npm run test:e2e`, then
`npm run qa:seed && npm run test:e2e:mobile`, then work through the relevant checklists.
